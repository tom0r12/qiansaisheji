# 10,450 task/s 目标的约束与候选路径

日期：2026-11-11。范围：独立只读核对题面、平台与当前冻结候选；本文件不修改 opt30，不代表实现、官方解释或 PPA 签核。计算值另存 `throughput_target_requirements_20261111.json`。

## 先确认需求和未决项

用户目标为 **吞吐量 > 10,450 task/s、增量面积 ≤ 0.5 mm²、单任务能耗 ≤ 6.3 µJ**，且共享 SRAM 访问必须经过总线。这些是本次设计目标；题面面积硬门槛实际为 2.25 mm²，不能混为一谈。

以下未决项直接决定方案是否可达，不能靠增加仿真次数消除。按用户本次无人值守要求，先查已有正式资料和平台实现，不向用户提问或擅自联系组委会；没有明确证据就保留 OPEN，采用原官方总线不改、无 SRAM 旁路的保守路径继续工作。涉及扩展权限的方案仅作条件研究，不能自行宣称获准：

1. “总线和外设采用组委会发布的平台工程”是否允许新增 System Bus segment、宽度转换、分银行并行互连，及改动原 fabric 的宽度/队列参数？哪些文件、参数必须保持原样？
2. 官方 loader 的确切入口、数据宽度、可接受吞吐、背压规则和开始事件是什么？“开始装载”从外部首次向共享 SRAM 写入算起，还是允许共享中已有本任务输入，再从共享到加速器的装载算起？初始装载是否与加速器共享同一个 32 位命令口？是否允许按队伍冻结格式紧凑传送、边加载边计算？
3. 如果所有原始加载写仍真实到达共享 SRAM，是否允许新增总线逻辑同时把成功写入的数据提交到加速器私有缓存，省掉一次后续共享读取？这仍需可核对的数据路由、错误/背压处理与面积统计，不能用测试平台代算或私有旁路替代总线。
4. 512 KB 共享 SRAM 的组织和端口数量是否固定？是否允许容量不变的银行并行/多端口组织？题面所列可用单/双端口 SRAM 宏明确针对加速器内部存储，不能据此直接断言共享 SRAM 可以改成双端口。
5. 紧凑 INT8 或其他数值格式输出能否按自定格式连续打包装载/写回，格式头、尺度及全部解码元数据如何计入？题面允许位宽选择，但实际 loader 与输出适配协议仍需落实。

在上述解释到来前，可以做有明确假设的分析和数值实验；不能把扩总线视为已经获准，也不能把“原参数不可改”视为题面逐字硬约束。

## 题面事实、平台现状与本轮工程选择

题面为工作区 `f8732a6ebb0442b1986eeec83a4bf6db.pdf`。下面同时列 PDF 物理页号与页脚号。

| 项目 | 证据 | 可以得出的结论 |

| 平台与接入 | 同页：“总线和外设采用组委会发布的平台工程”；AI 通过 System Bus 或 NICE 二选一接入 | 必须遵守原平台集成要求；仅给新互连命名为 System Bus 不足以证明合规 |

题面文本和示意图没有明确写“系统总线必须 32 位”“只能一个共享命令端口”“禁止新增任何并行 System Bus segment”或“所有 vendor 参数不可变”。但“采用发布的平台工程”确实限制自由改造，其具体边界需要官方解释。

### 关于装载起点的完整原文与解释边界

物理第 4 页/页脚 3，在系统时钟、共享 SRAM、常开域等平台要求之后，原文完整段落为：

> 系统采用分层参数装载。组委会提供参数加载仿真环境，通过平台已有访问接口向共享 SRAM 写入参数和输入数据；E203 执行驱动、调度及数据搬运，加速器完成本组规定的计算。全模型权重无需同时驻留共享 SRAM，不增设 DDR 或其他外部存储控制器。内部 SRAM 容量由参赛队根据面积与效率确定。

物理第 12 页/页脚 11，“3、吞吐量、功耗与面积的测量”中的任务定义与性能段落原文为：

> 本科一个任务为完成一次规定前馈线性层计算并写回结果；研究生一个任务为完成一次十二层编码器计算并写回结果。硬件计时不包含计算机端音频预处理、一次性文件格式转换和统一软件分类头执行。
>
> 性能测试在提交冻结后，由组委会从评测数据中统一抽取 12 个任务，同组采用相同输入。本科为覆盖 12 层参数的 12 次线性计算，每次均须单独满足 3% 的误差门槛；研究生为覆盖 12 个类别的 12 次十二层编码器计算。每个任务从输入和参数开始装载计时，至结果全部写回结束；任务开始前清空任务数据与参数缓存。参数装载、总线等待及 E203 调度时间全部计入，任务之间的测试平台复位时间不计入。
>
> 吞吐量等于完成任务数除以总运行时间，单位为任务/秒。平均功耗采用统一库、工艺角、负载、时钟与互连估计条件，根据同一计时窗口内的 SAIF 或 VCD 活动信息进行综合阶段估算；统计 E203、加速器、互连及 SRAM 的动态与静态功耗，模拟模块和片外设备不计入。活动信息须通过映射与覆盖检查，未标注电路不得按零活动处理，未建模 SRAM 不得按零功耗处理。

**原文事实**：必须计“输入和参数开始装载”之后的工作、总线等待和 E203 调度，且不能跨任务保留任务缓存。原文没有写“外部 host 首次写共享 SRAM 的握手”或“CPU 第一条 store”作为精确定义，也没有明确说“可以把共享 SRAM 预装放在窗外”。“任务数据与参数缓存”是否包括平台作为输入源的共享存储，也没有单独定义。

**此前采用的严格解释**：把第4页加载仿真环境向共享 SRAM 的首次真实装载也计入第12页窗口。这是结合两段的保守解释，不是已有官方起点信号确认，更不能仅凭该解释宣布其他起点已经被认定违规。

**需要确认的另一种解释**：平台预先向共享 SRAM 放好输入，任务从共享 SRAM 向加速器/私有缓存装载开始。若组委会明确采用这一边界，应据该边界重新测量；必须显式记录共享预装在窗外，不能与包含外部加载的数字混比。当前 source→live 工程 copy 是本地模拟选择，并非上述两种解释中任一种明确要求的步骤。

因此本文件把精确计时起点列为 **OPEN**。这不阻止独立数值、总线协议或条件性能实验，但在起点与 loader 实物/测试环境确认前，不能承诺10450的官方可比性。

当前平台确实为 32 位：`vendor/e203_hbirdv2/rtl/e203/core/e203_defines.v:68` 定义 `E203_XLEN=32`；`subsys/e203_subsys_mems.v:33` 起的 mem/sysmem ICB 数据口使用该宽度，124～127 行的主分发器为 `.DW(E203_XLEN)`、`.SPLT_FIFO_OUTS_NUM(1)`。同一文件 415 行另一条外部 AXI 转换路径还明确注释其 outstanding 参数可配置；这不是对主 mem splitter 的比赛授权，但也说明不能把所有源代码参数一概描述为规则禁止调整。

opt30 的 `qingyu_e203_subsys_main.v:850` 起与 `qingyu_icb_merge.sv:25` 起最终仍合流为一个 32 位命令口。读返回与写数据线虽分开，每笔读/写命令仍共享这一个接受机会。增加 outstanding、双缓冲或调度只能提高利用率，不能超过该口每拍接受一条 32 位命令的上限。

## 在哪些前提下可证明达不到

这里的物理下界是**有条件的证明**：150 MHz、每拍最多一条 32 位命令、初始写入与结果写回经过同一个命令口、当前冻结 INT16 布局、完整冷任务计时。改变其中任一条件都必须重新计算，不能把结论推广成任何合法架构都不可能。

当前一层数据为：

- X：99×64×2 = 12,672 B = 3,168 个 32 位词。
- W：64×256×2 = 32,768 B = 8,192 词。
- bias：256×8 = 2,048 B = 512 词（有效数值 INT48，当前存储容器为 64 位）。
- shift：256 B = 64 词。输入/参数合计 **11,936 词**。
- Y：99×256×2 = 50,688 B = **12,672 词**。

若只计算真实初始写入和最终输出写入，已经需要 24,608 次总线接受。即使读取私有缓存、计算和控制全免费：

`T ≤ 150,000,000 / (11,936 + 12,672) = 6,095.58 task/s`。

这是乐观上限，不是预计性能。若 loader 写入后还要逐词从共享 SRAM 读到私有缓存，则至少 36,544 次，理想上限下降到 4,104.64 task/s。bias 改用紧凑 48 位可减少 128 词，但不足以改变上述不可达结论。

若官方允许共享预装在窗外，当前 INT16 数据仍必须从共享 SRAM 至加速器完整读入一次，再写回全部输出；同一32位口下依然至少 `11936读取+12672写回=24608` 拍，恰好仍是6095.58 task/s上限。数值相同的两条界来自不同事务，不能相互混用解释。只有在装载捕获、位宽、路由或数据格式另有变化时，才需要重新推导。

| 情景 | 理想最低周期/任务 | 理想吞吐上限 task/s |
|---|---:|---:|
| INT16、32 位，初始写入＋输出，忽略所有其它工作 | 24,608 | 6,095.58 |
| INT16、32 位，再加共享到私有完整读取 | 36,544 | 4,104.64 |
| 当前 opt30 工程窗口的有效载荷（不含外部 preload） | 37,120 | 4,040.95 |
| 当前 opt30 再计已观察的 320 次 CPU 验证读取 | 37,440 | 4,006.41 |
| INT16、真正端到端 64 位，初始写入＋输出 | 12,304 | 12,191.16 |
| INT16、端到端 64 位，再加私有读取 | 18,272 | 8,209.28 |
| INT16、端到端 128 位，再加私有读取 | 9,136 | 16,418.56 |

宽总线各行假设所有相关数据传输都能够按该宽度打包，且总线和 SRAM 银行每拍可服务一次；不能把 32 位 loader 接到宽后端，就直接把 loader 的时间除以二或四。单独扩宽一个末端模块、而保留前面的 32 位串行瓶颈，也达不到表中数值。

还必须区分 loader 是仿真主机/硬件主设备还是 E203 软件循环。题面规定由组委会提供加载仿真环境，并没有规定 E203 必须执行11936条初始化store。若最终环境确实要求CPU逐词先load数据再store共享，普通直接拷贝至少涉及23872条数据访存指令，尚未计地址、循环、等待；单发射 E203 不可能把这些压入14354拍。新增128位加速器后端不会自动消除这个32位CPU前端瓶颈。反之，也不能在未见loader实现前，擅自以“CPU逐词初始化”作为题面必付代价。实际loader吞吐与计时起点应联合确认。

10,450 task/s 对应平均任务时长 95.69378 µs、14,354.06699 个 150 MHz 时钟；目标为“超过”，所以周期必须严格小于该值。当前 INT16 最低输入＋输出需要 1.714357 次 32 位传输/拍，即有效数据宽度至少 54.8594 bit/拍；若保留共享到私有再读，需要至少 81.4688 bit/拍。原单口 32 位峰值为 600 MB/s，最低输入＋输出目标已要求约 1.029 GB/s。

计算也是独立瓶颈：本层直接密集计算包含 1,622,016 次 MAC。当前四行×16=64 MAC/拍，即使零搬运，至少 25,344 拍，上限 5,918.56 task/s。目标要求平均 113.000448 MAC/拍，因此当前计算阵列也必须改变；常规 128 MAC/拍的理想下界为 12,672 拍，按 8 行块处理尾行至少 13,312 个 MAC 步，只剩约 1,042 拍容纳不能重叠的开销。上述是当前密集 MAC 算法的界，不是对所有可能算法的复杂度证明。

在恰好 10,450 task/s 时，6.3 µJ/任务对应全 SoC 平均功耗 65.835 mW。更高吞吐时应继续使用 `E=P/T` 判断，不能把这个功率值错误当作所有吞吐下固定门槛。新增互连、解包、宽 SRAM 适配和增加的计算并行都要计面积与功耗，目前没有可据以保证 ≤0.5 mm² 的新综合结果。

## 三条候选路径

| 路径 | 数据流及可达性 | 规则基础与风险 | 下一步证据 |
|---|---|---|---|
| A：保留原 32 位单口与 INT16，接正式 loader、单份共享数据 | 可删人为 source/live 副本，保留真实初始写入，增加队列及流水；但即使装载同时提交私有缓存也受 6,095.58 上限约束，**不能承担 10,450 目标** | 平台改动最小，作为可信基线和时窗校准路径；不能继续投入仅调度优化而承诺越过硬界 | 官方 loader 联调、完整窗口的逐笔与输出核对；确定当前格式真实上限 |
| B：保留 32 位接口，低位宽格式＋加载时提交私有缓存＋更高 MAC 并行 | 例如 X/W/Y 全 INT8，bias 仍64位容器、shift不变：初始6256词、输出6336词，单次加载捕获路径最低12592拍，上限11912.33；若仍再读全部输入则18848拍、仅7958.40，仍不达标 | 题面明确允许数值位宽；但 INT8 精度尚未验证，新增尺度/格式开销要计入；加载写捕获语义与官方接口需确认；约12%预算余量很窄，不保证可实现 | 训练集无梯度标定→冻结→独立验证；新的规范数值模型；至少128等价MAC/拍的真实周期/面积；合法冷加载捕获证明 |
| C：官方允许的更宽或并行 System Bus 与分银行共享存储 | 例如端到端128位、INT16、保留共享再读的传输下界9136拍；或64位配加载捕获下界12304拍。128位有较大总线余量，但仍需更强计算和充分重叠 | PDF 未明确禁止，也未明确授权；须确认扩段/改宽/共享银行和固定资源面积边界。所有通路必须是真实总线协议与仲裁，不能把旧直连改名。若官方loader固定32位，需重新建模，表中宽口假设不成立 | 官方书面边界；端到端拓扑/周期模型；输入输出全部经批准总线；最终同网表多角时序、宏功耗和新增逻辑面积 |

优先顺序：立即厘清官方 loader/总线变动边界，同时可研究 B 的低位宽数值误差；A 保留作比较基线。只有规则和精度证据支持后，才在 B/C 中选实现。不要以尚未验证的 INT8 精度、银行无冲突、完美重叠或未知 SRAM 功耗作为满足三个目标的事实。

表中 B/C 的装载数字采用此前严格解释。若官方最终采用共享预装在窗外的解释，B 的6256词可改为窗内共享读取，而不是要求窗内loader写入捕获；此时同样得到12592拍的基础流量，但必须确保私有缓存从空开始，且全部必要共享读取已计入。C也须按官方入口重新计算，不能拿两个不同计时解释的最佳部分拼接。

## 比较与验收边界

所有性能结果都必须是一整个 99×64×256 任务；官方认定的装载起点之后，加载、E203 调度、总线等待、所有输出写入及响应必须处于同一窗口。精确装载起点目前为OPEN，严格解释的实验应计外部共享写入；其它起点须注明并获得官方明确口径后才可与正式结果比较。任务前缓存清空；不同独立任务不得借权重驻留省装载。压缩/低位宽所需的硬件解包与提交格式需要说明，不得在评测端代算必做矩阵结果。

现有 opt30 的 92,372.67 工程周期、假设150 MHz下1,623.86 task/s，仍是行为 SRAM、外部 source 初始化在窗外的本地证据。它与未来官方 loader 窗口不直接构成成绩比较。面积0.5 mm²和6.3 µJ的目标也不能用历史旁路0.38 mm²/7 µJ代替测量。

本次未改任何冻结 RTL/固件，未改变题目指标，未访问其他参赛者数据。上述上限仅用于淘汰不可能的配置、确定设计前提；没有任何方案被宣称已经达到目标。
